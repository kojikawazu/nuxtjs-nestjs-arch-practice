## 機能詳細

| 機能 | 入力 | 処理 | 出力 |
|------|------|------|------|
| 登録 | email / password / displayName | 重複確認 → bcrypt ハッシュ → ユーザー作成 → トークン発行 | AuthTokens(201) |
| ログイン | email / password | ユーザー照合 → パスワード検証 → トークン発行 | AuthTokens |
| リフレッシュ | refreshToken（Cookie 経由） | ハッシュ照合 → 旧トークン失効（消せた場合のみ）→ 再発行 | AuthTokens（同一トークンの並行使用は 1 本だけ成功し、他は 401） |
| タスク作成 | title / description? / status? / startDate / endDate? / url? | DTO 検証（url は http/https のみ）→ 開始≤終了確認 → 保存 | Task(201) |
| タスク更新 | 上記の部分集合 | 所有確認 → マージ → 開始≤終了確認 → 保存 | Task |
| 画像添付 | multipart `file` | 所有確認 → MIME/サイズ検証 → uuid 名で保存 → DB 保存 → 旧ファイル削除（DB 保存に失敗したら新ファイルを補償削除） | Task |

## ユーザーフロー

1. 未認証で `/tasks` へアクセス → `/login` へリダイレクト。
2. 登録/ログイン成功 → アクセストークンをメモリ保持、`/tasks` へ。
3. アクセストークン失効後の操作: API が 401 を返した時点で**自動的にリフレッシュして同じ操作を再試行する**（利用者はリロード不要）。再試行は 1 回だけで、リフレッシュできない場合はセッション（メモリ + Cookie）を破棄して `/login` へ戻る。
4. 新規作成: フォーム入力 → 「確認へ」で confirm 画面 → 「作成する」で確定 → 詳細へ。サーバ側の業務ルール違反（開始 > 終了 など）は「作成する」の実行時にエラーとして返る。
   - **両版とも独立ルート `/tasks/new/confirm`** に遷移する。draft の保持先だけが異なり、`frontend-spa` は sessionStorage（クライアント描画）、`frontend-ssr` は httpOnly Cookie（サーバ描画）（→ [09 確認画面の方式差](./09-architecture-specification.md#確認画面の方式差ssr--csr)）。どちらもリロード・直リンクで内容が残り、「修正する」で入力値が復元される。ただし**別タブで確認画面を開くと spa 版だけ復元できない**（sessionStorage はタブ単位）。
   - 検証失敗（422）は入力画面へ差し戻し、フィールド別のインライン表示にする（確認画面には入力欄が無いため）。
   - **作成が通った時点で draft を破棄する**。タスク本体の作成（`POST /tasks`）と画像添付（`POST /tasks/{id}/image`）は別 API なので、本体成功・画像失敗という部分成功が起こりうる。draft は「もう一度作成する」ための唯一の入力源なので、作成成功の直後に消すことで、押し直し・リロードのどちらでも二重作成が起こらないようにしている。
   - 部分成功時は確認画面に留まり、「タスクは作成されました。画像の添付だけ失敗しました」と伝えたうえで、**再作成ボタンは出さず**「画像を再送する」「画像なしで完了する」の 2 択を出す。
5. 編集: 既存値をフォームに反映 → confirm → 確定。画像は差し替え/削除も可能。更新は `PATCH`（冪等）なので、画像失敗時はフォームへ戻して差し替えられる。
   - **任意項目（説明 / 終了日 / 関連 URL）は空欄にすれば削除できる**。フォームは空欄を `null`（＝明示的に空にした）として送出し、`PATCH` はそれを削除指定として扱う。空欄を `undefined` にすると「触っていない」と区別がつかず、確認画面では空に見えても保存後に元の値が復活する。
   - 新規作成では消す対象が無いため、空欄はキーごと省略して送る（従来どおり）。
6. 削除: 詳細で確認ダイアログ → 実行 → 一覧へ。**添付画像があれば実ファイルも削除する**（DB → ストレージの順。逆順だと DB 削除の失敗で「レコードはあるのに実体が無い」リンク切れになるため）。

> **孤立ファイルを残さない**（削除・添付の両方向）。削除は「DB → ストレージ」の順にすることで、失敗しても残るのは参照されない孤立ファイルだけになる。**添付は逆順にできない**（`imageUrl` を決めるためにファイル生成が先に要る）ため、DB 保存に失敗したら**直前に書いた新ファイルを補償削除**する。補償削除自体が失敗しても握りつぶし、**元の保存エラーを投げ直す**（原因が「保存に失敗した」から「掃除に失敗した」へすり替わると調査が迷子になるため）。

## UI/UX 仕様

- 画面: ログイン / 登録 / タスク一覧 / タスク詳細 / 新規作成 / 編集。
- 一覧カードはタイトル・状態・説明のみ表示（画像は出さない）。画像は詳細・確認画面・編集フォームでプレビュー。
- 作成/更新は 2 段階（フォーム → 確認）。クライアント側の入力検証（zod `taskFormSchema`）はフォームで即時にフィールド別エラーを出す。サーバ側の業務ルール違反は確定ボタン実行時にエラーとして表示する。
  - `frontend-ssr` は入力内容を httpOnly Cookie に保持する都合上、直列化サイズの上限がある（日本語で約 380 文字相当）。文字数上限とは別基準のため、**入力中にインラインで警告し submit をブロックする**（超過したまま送信して初めて弾かれる体験にしない）。`frontend-spa` は sessionStorage のため実質的な上限がなく、この警告は出ない。
- 関連 URL（任意）はフォームで入力し、確認画面・詳細で**安全なリンクカード**としてプレビュー表示する。`http`/`https` のみ許可（`javascript:`/`data:` 等は入力検証でエラー、描画時も `<a>` を出さない）。クリックは別タブ（`target="_blank" rel="noopener noreferrer"`）で開く。
- 日付は flatpickr の 2 入力（開始・終了）。クライアント側でも開始必須・開始≤終了を検証。

## ビジネスロジック

- 認可: タスクは所有者のみ操作可。存在しない=404 / 非所有=403 を区別。
- 日付: `startDate` 必須（日付のみ・午前0時 UTC）、`endDate` 任意。両方ある場合は `startDate ≤ endDate`（違反 422・`errors[].field` は `endDate`）。更新時はマージ後の値で判定。
- 状態: `todo` / `in_progress` / `done`。未指定の作成時は `todo`。
- 画像: 1 枚・任意。保存ファイル名はサーバ生成（`<taskId>-<uuid>.<ext>`）。`imageUrl` は `Task` のみが持つ（クライアントから直接設定不可）。
- トークン: アクセスは短命（既定 900s・メモリ保持）、リフレッシュは長命（既定 7d・httpOnly Cookie・ローテーション）。フロントは 401 を受けたら 1 回だけリフレッシュして再試行する（→ [06 認証](./06-security-specification.md#認証)）。
