# 非機能仕様書

性能・可用性・信頼性・保守性など、機能以外の品質要件を定義するドキュメント。

> 学習用プロジェクトのため、定量的な SLA は設けず「設計上どう担保しているか」を記す。

## パフォーマンス

- 一覧は自分のタスクのみを作成日降順で取得（`userId` にインデックス）。ページネーションは未実装（対象外）。
- アップロード画像はサイズ上限 2MB。`imageUrl` は静的配信され、API を経由しない。

## スケーラビリティ

- backend は状態をメモリに持たない（リフレッシュトークンは DB ハッシュ保存）ため水平スケール可能な設計。
- ただし画像はローカルファイルシステム保存のため、本番で多インスタンス化する場合は共有ストレージ（オブジェクトストレージ等）への移行が前提（現状は対象外）。

## 可用性

- `GET /health` で死活監視。compose では MySQL の healthcheck 通過後に backend を起動。
- 学習用のため稼働率目標は定めない。

## 信頼性

- データ整合性: 認可（所有者チェック）と DTO バリデーションで不正データを拒否。日付の整合（開始≤終了）を Service で担保。
- 画像: 保存成功後に旧ファイルを削除し、削除失敗は本処理を巻き戻さない（掃除の失敗で更新を失敗扱いにしない）。
- バックアップ/リカバリ方針は未定義（対象外）。本番 DB は volume、画像も volume で永続化。

## 保守性・運用

- レイヤード構成（presentation / application / infrastructure）でビジネスロジックを Service に集約。
- 契約（TypeSpec）を単一の真実とし、型・クライアント・Swagger を生成して FE/BE の齟齬を防ぐ。
- 例外は `AllExceptionsFilter` で契約 `ApiError` 形に統一（内部情報を漏らさない）。
- 設定は環境変数（`.env`、`.env.example` をテンプレート提供）。`DB_TYPE` で MySQL / SQLite を切替。
- 品質ゲート: lint / format / 各層テスト。テストは「正常系 1 : 異常系 2 以上」「外部 I/O のみモック」を原則とする。
- 既知の負債: 学習用に `synchronize: true`（本番はマイグレーション運用へ）、CI 未整備。
