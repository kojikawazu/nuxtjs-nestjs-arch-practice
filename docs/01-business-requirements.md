## 背景

Nuxt.js + NestJS のモノレポで「アーキテクチャの違いが実装にどう現れるか」を学ぶことを主目的とした練習プロジェクト。題材として実用的なテーマが必要なため、認証付きのタスク管理アプリを採用している。

アーキテクチャの違いは文章で読んでも身につきにくい。**同じ機能・同じ API 契約を複数のアーキで実装して並べ、差分として読む**ことをこのプロジェクトの中心に据える。したがって学習対象はアプリ機能そのものではなく、契約駆動（TypeSpec）を前提としたうえでの層構成・依存方向・ドメインロジックの置き場所の選択と、その選択がもたらすトレードオフである。

当初はテストの書き分けを主目的として開始し、バックエンド 1 版・フロントエンド 1 版で始めた。実装が 3 アーキ × 2 レンダリング方式へ広がった時点で主目的をアーキテクチャ比較へ移し、リポジトリ名も `nuxtjs-nestjs-test-practice` から `nuxtjs-nestjs-arch-practice` へ改めた（2026-09-04）。テストは目的の座から降りたが、**アーキを入れ替えても外から見た仕様が変わらないことを証明する装置**として引き続き必須である。

## 目標

- 認証 + タスク CRUD という小さな題材を、**layered / clean / onion の 3 バックエンド**と **SPA / SSR の 2 フロントエンド**で実装し、設計差をコードの差分として読めるようにする。
- 契約（TypeSpec → OpenAPI → 型/クライアント生成）を単一の真実とし、全実装が同一の契約を満たす（＝比較の土台をそろえる）。FE/BE の型ズレも構造的に防ぐ。
- **同じ e2e シナリオが全バックエンド実装で通る**ことを維持し、「外から見た挙動は同一・内部構造のみ異なる」状態を機械的に担保する。
- 層の依存方向を規約ではなく ESLint で機械強制し、アーキの境界が時間とともに崩れないようにする。
- 上記を支えるテストを UT / IT / e2e / シナリオのレベルで書き分け、「ビジネスロジックはモックしない・外部 I/O のみモック」「正常系 1 : 異常系 2 以上」を維持する。

## ステークホルダー

- 利用者: 学習者本人（開発者）。
- 意思決定者: 同上。外部顧客や運用組織は想定しない（学習用）。

## スコープ

### やること

- ユーザー登録 / ログイン / トークンリフレッシュ / ログアウト（JWT）。
- タスクの CRUD（所有者のみ操作可）、開始/終了日、状態（todo/in_progress/done）。
- タスクへの画像添付（1 枚・任意）。
- 上記を **layered / clean / onion の 3 バックエンド**と **SPA / SSR の 2 フロントエンド**で実装し、比較できる状態に保つ。
- 各層のテストと、契約から生成した Swagger UI。
- CI（GitHub Actions）で lint / format / 型チェック / 各レベルのテストを自動実行し、全実装の同一性を機械的に検証する。

### やらないこと（対象外）

- **比較軸にならないアーキの追加**（既存 3 版と差が説明できないもの）。実装が増えるほど同一性の維持コストが全実装に掛かるため、比較して学べる差があるものだけを足す。
- 複数ユーザー間の共有・コラボレーション、ロール/権限管理。
- タスクの検索・ページネーション・並び替え（一覧は作成日降順固定）。
- 本番運用向けのスキーマ管理（マイグレーション）と監視基盤。スキーマは TypeORM の `synchronize` で追従させる（`DB_SYNCHRONIZE`）。
- 画像の複数枚添付・サムネイル生成・外部オブジェクトストレージ連携。

## 制約

- 学習用のため予算・期限の制約は設けない。
- DB はカラム型を MySQL / SQLite 双方で動くポータブルな型に限定（enum カラム禁止）。
- 本番は MySQL、ローカル/テストは better-sqlite3（インメモリ）を `DB_TYPE` で切替。
- 画像はオブジェクトストレージ専用コンテナを使わず、backend のファイルシステム + volume に保存する。
