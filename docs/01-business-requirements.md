# 要求仕様書

プロジェクトの背景・目標・スコープを定義し、何を・なぜ作るのかの合意を形成するドキュメント。

## 背景

Nuxt.js + NestJS のモノレポで「各層にどんなテストを・なぜ書くか」を学ぶことを主目的とした練習プロジェクト。題材として実用的なテーマが必要なため、認証付きのタスク管理アプリを採用している。学習対象はアプリ機能そのものよりも、契約駆動（TypeSpec）・レイヤード設計・テスト容易性を意識した設計と、それを裏付けるテスト群である。

## 目標

- 認証 + タスク CRUD という小さな題材で、BE 単体 / BE e2e / FE 単体 / 全体 E2E の各テスト層を実際に書き分ける。
- 契約（TypeSpec → OpenAPI → 型/クライアント生成）を単一の真実とし、FE/BE の型ズレを構造的に防ぐ。
- 「ビジネスロジックはモックしない・外部 I/O のみモック」「正常系 1 : 異常系 2 以上」を満たすテストを維持する。

## ステークホルダー

- 利用者: 学習者本人（開発者）。
- 意思決定者: 同上。外部顧客や運用組織は想定しない（学習用）。

## スコープ

**やること**

- ユーザー登録 / ログイン / トークンリフレッシュ / ログアウト（JWT）。
- タスクの CRUD（所有者のみ操作可）、開始/終了日、状態（todo/in_progress/done）。
- 保存前の事前検証（DryRun）エンドポイント。
- タスクへの画像添付（1 枚・任意）。
- 各層のテストと、契約から生成した Swagger UI。

**やらないこと（対象外）**

- 複数ユーザー間の共有・コラボレーション、ロール/権限管理。
- タスクの検索・ページネーション・並び替え（一覧は作成日降順固定）。
- 本番運用向けのマイグレーション、CI、監視基盤。
- 画像の複数枚添付・サムネイル生成・外部オブジェクトストレージ連携。

## 制約

- 学習用のため予算・期限の制約は設けない。
- DB はカラム型を MySQL / SQLite 双方で動くポータブルな型に限定（enum カラム禁止）。
- 本番は MySQL、ローカル/テストは better-sqlite3（インメモリ）を `DB_TYPE` で切替。
- 画像はオブジェクトストレージ専用コンテナを使わず、backend のファイルシステム + volume に保存する。
