# 静的解析の運用

どのツールを使うかは [coding-standards.md](./coding-standards.md)（ESLint / Prettier / TypeScript）と [github-actions.md](./github-actions.md)（actionlint）で定める。本ルールは**どう運用するか**を定める。

## 本リポジトリの検査一覧

| 対象 | ツール | 実行 | 設定の正本 |
|---|---|---|---|
| TypeScript / Vue | ESLint | `pnpm lint` | `eslint.config.mjs` |
| コード整形 | Prettier（`--check`） | `pnpm format:check` | `.prettierrc.json` / `.prettierignore` |
| 型 | `tsc --noEmit` | `pnpm -r typecheck` | 各 `tsconfig.json` |
| Markdown | markdownlint-cli2 | `pnpm lint:md` | `.markdownlint-cli2.yaml` |
| ワークフロー | actionlint（Docker） | `pnpm lint:workflows` | イメージタグで固定 |

## 役割分担（重ねない）

| 種類 | 役割 | 議論の対象 |
|---|---|---|
| **Formatter** | 見た目（インデント・改行・引用符）を機械的に統一する | **しない**。既定設定に従う |
| **Linter** | バグの温床・危険なパターンを検出する | ルールの追加・除外のみ議論する |
| **型チェッカ** | 型の不整合を検出する | しない |

- **見た目に関する Linter ルールを有効にしない**。Formatter と競合し、直しても直らないエラーが出る。
- **整形役が居ない対象では、見た目のルールを有効にしない**。本リポジトリは `.prettierignore` で `*.md` を除外している（表の桁揃えで差分が肥大し、内容の差分がレビューで埋もれるため）。したがって Markdown には整形役が居らず、行長（MD013）や表のパイプ揃え（MD060）を有効にすると**手で直し続けることになる**。実際、導入時の違反 796 件のうち 751 件がこの 2 つだった。
- **フォーマットの好みをレビューで指摘しない**。Formatter の出力が正で、指摘が出る状態は設定不足のサイン。

## 警告ゼロを維持する

- **Linter・Formatter・型チェックはすべて CI で実行し、違反があればマージをブロックする**。ローカル任意実行にしない。
- **警告を放置しない**。「出るが動く」状態が常態化すると、新しい警告が埋もれて**検出装置として機能しなくなる**。守れないルールは `error` にするか無効にするかの二択で、中間の「警告のまま放置」を作らない。
- Formatter は**差分ゼロを検証**する（`--check`）。CI がコードを自動整形してコミットし返す運用にしない。
- 型チェックは**ビルドとは別に明示実行**する（`tsc --noEmit`）。バンドラの型スキップ設定で見逃さないため。

## 抑制コメントの扱い

`eslint-disable` / `@ts-expect-error` / `<!-- markdownlint-disable -->` / `# shellcheck disable` などの抑制は**例外的な手段**として扱う。

- **理由をコメントで必ず書く**（[jsdoc.md](./jsdoc.md) の「why コメント必須」と同じ原則）。理由のない抑制は差し戻す。
- **範囲を最小にする**。ファイル全体ではなく該当行のみ。ファイル先頭での一括無効化をしない。
- **抑制するルール名を明示する**。ルール名なしの全ルール抑制をしない。
- `@ts-ignore` ではなく **`@ts-expect-error` を使う**（問題が解消したとき「不要な抑制」として検出され、抑制が残り続けない）。
- 同じ抑制が**何箇所にも増えたらルール設定自体を見直す**。実態に合わないルールを抑制コメントで回し続けない。

## ルール設定の変更

- **無効化するルールには、設定ファイルに理由をコメントで残す**。「なぜこのプロジェクトでは守れない／守る意味がないのか」を書く。`.markdownlint-cli2.yaml` の各エントリがその形。
- **抑制コメントで違反を消さない**。ルール単位で無効化するか、違反そのものを直すかのどちらかにする。個別ファイルに抑制を撒くと、無効化の判断が設定ファイルから読めなくなる。
- 既存コードへ厳しいルールを導入して大量の違反が出る場合、**一括抑制せず、無効化するルールと直す違反を仕分ける**。導入時に「見た目のルールは無効化・壊れているものは修正」で仕分けた結果、連番の飛び（MD029）とリンク切れ（MD051）という**実バグが 2 件見つかった**。
- 設定ファイルは**コミット対象**。ローカル固有設定に依存しない。

## レビュー観点

- 抑制コメントに理由が書かれているか。範囲・ルール名が最小限に絞られているか。
- 違反を抑制コメントで消していないか（ルール単位の無効化 or 修正になっているか）。
- 無効化したルールの理由が設定ファイルに書かれているか。
- Formatter が直すべき見た目をレビューで指摘していないか（＝設定不足のサイン）。
- 警告が出たまま放置されていないか。
